왜 기존 영화 추천은 내 취향과 어긋날까?

SLIDE 02 / 07

🚨 Problem: 기존 영화 추천 서비스의 3가지 한계

  • 타인의 평점·리뷰 편향 (Review Bias): 대중적인 흥행작이나 평론가 리뷰가 추천 알고리즘에 과도하게 개입되어 이용자 고유의 호불호가 희석됨
  • 유명 배우·감독 편중 (Star Power Dependency): 주연 배우나 유명 감독 위주로만 묶여서 추천되기 때문에, 덜 알려진 명작(Hidden Gem)은 추천 풀에서 배제됨
  • 영화의 '결'을 좌우하는 세부 정보 누락: 영상미(촬영 감독), 배경 음악(음악 감독), 액션 스타일(무술 감독) 등 실제 몰입감을 결정하는 스태프 및 복합 장르 특성이 반영되지 않음

💡 Solution: Voo-ong의 데이터 엔지니어링 접근법

  • 순수 개인 평가 기반 선호도 재정의: 타인의 리뷰 텍스트를 배제하고, 이용자 본인의 평점 분포를 MinMaxScaler 및 4:2:4 구간화(긍정 +1 / 중립 0 / 부정 -1)로 변환하여 개인별 선호 기준점 확립
  • 3대 영화 데이터베이스 스키마 통합: 글로벌 데이터셋(MovieLens 평점·태그 게놈, IMDb 영화·인물·직군)과 한국어 서비스용 네이버 영화(크롤링)를 단일 RDB/Hive 구조로 통합
  • 세밀한 메타데이터(직군·장르) 벡터화: 인물별 상세 직군(professions)과 37개 표준 통합 장르(voo_ong.genres)를 매핑하여 정교한 취향 프로파일링 구현

⚡ 핵심 구현 1: 멀티스레딩 + 실패 자동 재시도(Retry) 크롤러

단일 스레드 크롤링의 속도 한계를 극복하기 위해 ThreadPoolExecutor를 도입하고, 네트워크 순단으로 누락된 영화 코드만 모아서 재시도하는 복원력(Resilience) 로직을 구현했습니다.

# Apps/pylib/crawler.py 핵심 발췌
class Crawler:
def __init__(self, settings):
self.max_workers = os.cpu_count() * 5 if isinstance(os.cpu_count(), int) else 8
self.executor = ThreadPoolExecutor(max_workers=self.max_workers)

def thread_executor(self, func):
retry_count = 5
while True:
tqdm_list = list(tqdm(self.executor.map(func, func_args), total=len(search_range)))
failure_list = [d["code"] for d in tqdm_list if d["status"] == "Fail"]
if failure_list and retry_count != 0:
func_args = ((self.headers, code) for code in failure_list)
retry_count -= 1  # 실패한 코드만 큐에 재투입하여 최대 5회 재시도
continue
break
# 봇 탐지 우회를 위한 소수점 단위 비정규 난수 대기: time.sleep(random.random() + random.randint(0, 3))

2,800만 건 평점을 순회하며 긍정(+1) 평가 영화의 장르는 더하고 부정(-1)은 차감하여 개인별 19개 장르 점수(ratings_genres) 산출

🧮 이용자별 장르 선호도 집계 알고리즘 (이용자별 장르 평점 계산/main.py)

# Hive(PyHive)에서 전처리 테이블 로드 후 이용자별 19개 장르 가중치 합산
def ratings_aggregator(func_args):
user_id, movie_id, rating = rating_df.at[index, "user_id"], ...
if rating == 1:     # 긍정 평가(+1) 시 해당 영화의 원-핫 장르 벡터 가산
for genre in genres_columns:
temp_df.at[0, genre] += movies_genres_onehot[
movies_genres_onehot["movie_id"] == movie_id
][genre]
elif rating == -1:  # 부정 평가(-1) 시 해당 영화의 원-핫 장르 벡터 차감
for genre in genres_columns:
temp_df.at[0, genre] -= movies_genres_onehot[
movies_genres_onehot["movie_id"] == movie_id
][genre]
return temp_df

  • 선호 영화 타겟 필터링: 모델이 '이용자가 실제로 선호하는 영화의 장르 조합'을 학습하도록 부정 평가(-1) 레코드를 제외한 2,275만 건의 유효 데이터셋 구축

TROUBLESHOOTING 01

클라우드 과금 폭증(월 100만 원) 위기와 온프레미스 피벗

[해결] 즉시 클라우드 리소스를 정리하고, 로컬 고사양 PC에 VirtualBox 기반 CentOS 7 클러스터(노드당 16GB RAM, 4 vCPU, 듀얼 네트워크 고정 IP)를 구축하여 비용 0원으로 오히려 더 높은 연산 사양의 분산 처리 환경을 완성했습니다.

TROUBLESHOOTING 02

Hadoop 배포판 빌드/라이선스 제약 및 Sqoop 파싱 오류 해결

[문제] ① Ambari 2.7.5 및 Cloudera 6.3.3 이후 버전의 유료화 정책 변경 및 의존성 빌드 실패, ② MySQL에서 Hive로 원-핫 인코딩 데이터를 이관할 때 Apache Sqoop이 특수문자를 처리하지 못하는 오류 발생.
[해결] 공개 아카이브를 역추적하여 Ambari 2.7.4 및 Cloudera 6.3.1 저장소를 확보해 클러스터를 구축하고, Sqoop 특수문자 에러 구간은 HiveQL DDL/DML 스크립트 직접 실행 및 컬럼명 정규화(소문자·언더스코어 변환)로 우회 해결했습니다.

TROUBLESHOOTING 03

글로벌(IMDb)-국내(네이버 영화) 데이터 통합의 한계 규명 및 표준화

[문제] 한국어 서비스 제공을 위해 네이버 영화를 크롤링해 MySQL에 적재했으나, IMDb의 영문 영화명/인물명 표기와 네이버 영화의 영문 표기 규칙이 불일치하여 100% 자동 조인이 불가능한 데이터 정합성 이슈를 발견했습니다.
[해결] 먼저 3개 플랫폼의 상이한 장르 체계를 아우르는 37개 통합 장르 매핑 테이블(voo_ong.genres)을 구축하여 장르 기반 추천 파이프라인을 완성하고, 이기종 데이터 간 식별자(Key) 표준화의 중요성을 실증적으로 도출했습니다.
